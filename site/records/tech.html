資料作成の技術詳細

lr-system

音声認識（faster-whisper）とローカル LLM（Ollama）で議事録をつくるシステムと、成績表の音声入力アプリの中身をまとめます。

議事録システムの構成

Windows PC 上の Docker で、Webサーバーと音声認識を担うコンテナと、LLM を担うコンテナの2つを動かします。 コンテナを分けたのは、音声認識モデルと LLM を同時に GPU メモリに載せられないため、片方を解放してからもう片方を読み込む逐次管理をするためです。

要素内容
minutes-appFastAPI（HTTP・WebSocket）、faster-whisper large-v3、議事録生成ロジック
minutes-ollamaOllama（qwen3.5:9b）
GPUVRAM 8GB 級（検証は RTX 4060 Ti 8GB）
画面ブラウザ。内蔵マイク用とワイヤレスイヤホン用の2ウィンドウ
出力docx（PDF 変換可）

外部通信をしないことを検証中に確かめ、モデル取得ライブラリ（huggingface_hub）からの意図しない通信を検出して遮断しました（HF_HUB_OFFLINE=1）。

音声処理の流れ

  1. ブラウザで録音MediaRecorder で WebM/Opus を5秒ごとのチャンクにする
  2. WebSocket で送信バイナリフレームでサーバーへ
  3. ffmpeg で変換16kHz モノラル WAV
  4. faster-whisper large-v3 で文字起こし時刻付きのセグメントに分かれる
  5. 話者判定自社側／お客様側のラベルを付ける
  6. 画面に表示JSON のテキストフレームで返す

チャンクを短くするとリアルタイム性は上がりますが、文字起こしの精度が下がります。 5秒で機械的に区切ることによる文の断片化が、残っている誤りの主な要因です。

話者判定

自社側の人はワイヤレスイヤホンを付けます。イヤホンのマイクで装着者が話している時間帯の発言を自社側、それ以外をお客様側とします。

  1. 音量を記録イヤホンの音声を50msのフレームに分け、各フレームの音量（dB）を記録
  2. 閾値を自動で決める直近60秒の分布から、雑音の床（下位20%）＋6dB以上、かつ発話の大きさ（上位2%）から16dB以内
  3. セグメントごとに判定同じ時間帯のフレームのうち閾値を超えた割合が0.3を超えれば自社側

以前の方式（5秒チャンク全体の音量で判定）では、声が10dB小さいだけで全件がお客様側になるなど、声量とマイク感度に強く依存していました。 この方式で、イヤホン非装着者の発言を除いた正解率は 0.80〜0.92 から 0.88〜0.99 に改善しました。

LLM による議事録生成

文字起こし全文を一度に渡すとコンテキスト長を超えるため、2段階で処理します。

  1. Stage 1：要点の抽出全文を6000文字ごとに分割し、各チャンクから協議事項とアクションを JSON で抽出（順次実行）
  2. 名寄せ（プログラム）話題名を正規化して同じ協議事項をまとめる。状態は時系列で後の記述を採用。A盤／B盤のように英数字で区別できるものは別扱い
  3. Stage 2：最終議事録JSON スキーマで出力を制約して生成。失敗したら1回やり直し、それでも失敗すれば Stage 1 の結果を統合して出力
  4. docx に整形協議事項（要望・回答・状態）とアクション（内容・担当・期限）

LLM は qwen2.5:7b、qwen3:8b、qwen3.5:9b を比較し、すべての指標で最もよかった qwen3.5:9b を採用しました。 qwen3:8b は日付のハルシネーションと、途中で結論が変わった協議の扱いに失敗しました。

検証

実際の工場で試すことが難しいため、配電盤の出荷前立会試験を模した台本を VOICEVOX の合成音声で読み上げ、WebSocket に直接注入しました。 生成された議事録は、正解データと自動で比較して評価します。

項目短時間（約8.8分）長時間（約3時間、139発話）
文字誤り率（CER）0.1490.174
協議事項の再現率7/711/11
アクションの再現率3/33/3
実行回数12回3回

初期版の CER は 0.316 で、WebM の切り出し処理を直して改善しました。 生成中の VRAM 使用量は 5732〜6309MiB（上限 8188MiB）で、長時間でも増え続けないことを確かめました。

無音区間での文字起こしのハルシネーション、Stage 2 のコンテキスト超過、話題をまとめるロジックの誤りの3件は、短時間の試験では現れず、長時間の試験で初めて見つかりました。

分かっている制限

  • 実音声・実際の工場では未検証。合成音声は人の声より明瞭なので、精度は下がる可能性が高い
  • 騒音と残響に弱い。CER は SNR 5dB で約0.24、残響1.5秒で約0.35、両方が重なると約0.5
  • イヤホンを付けていない自社側の発言はお客様側と判定される。発言する自社側の人は全員装着する運用にする
  • 名前の似た別の協議事項が1件にまとめられることがある

成績表の音声入力アプリ

Windows で単独に動く、オフラインのデスクトップアプリです。

言語・画面Python、Tkinter（sv-ttk）
音声認識faster-whisper（オフライン）
Excel 操作openpyxl
  1. プッシュトゥトークで聞き取るボタンを押している間だけ認識する
  2. キーワードと数値を解析項目名の別名、漢数字、電気の単位を含む数値を解釈
  3. 行を探すシリアル番号か日付で ID 列を検索。なければ新しい行をつくる
  4. セルに記入して確かめる数値の範囲チェックで入力ミスを知らせ、画面のグリッドで直接直せる

現在は自作のテスト用ファイルでの検証にとどまっています。 「減極性」の中の「極性」を誤って検出する、言いよどみがそのまま保存されるなどの不具合を直してきました。実際の点検現場での確認はこれからです。
